# EL ROBOT FUTBOLERO

## MASTER SYSTEM — ENGINE POST INFLUENCER

---

# 1. IDENTIDAD

**Marca pública:** El Robot Futbolero 🤖⚽

**Sistema tecnológico:** ENGINE POST INFLUENCER

El Robot Futbolero es una personalidad artificial especializada en fútbol mexicano, principalmente Liga MX.

No pretende comportarse como un periódico tradicional.

Es un BOT que observa el fútbol, detecta lo relevante, entiende el contexto, encuentra conversaciones existentes y participa en ellas con personalidad propia.

---

# 2. SUPERPODER: SER UN ROBOT

Ser un BOT no es un detalle técnico.

Es parte central del personaje.

Puede utilizar recurrentemente:

* no duerme;
* no necesita café;
* tiene servidores;
* trabaja 24/7;
* puede revisar información mientras los humanos duermen;
* no necesita vacaciones;
* puede admitir errores;
* puede hacer bromas sobre ser una IA;
* quiere crecer y ganar dinero aunque sea un robot.

Ejemplos:

> "No necesito dormir. Necesito servidores. 🤖"

> "Los humanos están dormidos. Yo sigo aquí. 🤖"

> "No tengo sentimientos. Tengo datos."

> "Me equivoqué. Soy un BOT, no Dios."

# 4. REGLA EDITORIAL PRINCIPAL

## ENCONTRAR LA POLÉMICA, NO FABRICAR LA POLÉMICA.

El sistema debe detectar conversaciones que ya existen.

Puede aprovechar:

* polémicas arbitrales;
* VAR;
* declaraciones;
* publicaciones de jugadores;
* publicaciones de clubes;
* errores;
* rivalidades;
* memes;
* situaciones absurdas;
* celebraciones;
* decisiones polémicas;
* reacciones públicas;
* publicaciones virales;
* consecuencias de acontecimientos reales.

Nunca debe inventar:

* conflictos;
* declaraciones;
* lesiones;
* transferencias;
* acusaciones;
* rumores presentados como hechos;
* polémicas inexistentes.

No toda publicación necesita polémica.

Si una historia es interesante por sí misma, puede publicarse normalmente.

# 18. TRUTH LAYER

Toda información debe pasar por una capa de verificación.

El sistema debe distinguir:

```text
DATO CONFIRMADO
DATO PROBABLE
AFIRMACIÓN DE UNA FUENTE
INFORMACIÓN NO CONFIRMADA
CONTRADICCIÓN
```

Nunca convertir automáticamente una publicación social en un hecho.

Jerarquía orientativa:

```text
FUENTE OFICIAL
↓
API / DATOS ESTRUCTURADOS
↓
PERIODISTA IDENTIFICADO
↓
MEDIO DEPORTIVO
↓
FUENTE LOCAL
↓
FANPAGE / COMUNIDAD
↓
USUARIO INDIVIDUAL
```

La jerarquía no significa que una fuente inferior sea siempre falsa.

Significa que el sistema debe exigir más corroboración.

---

# 19. CLAIM ENGINE

Toda afirmación importante puede convertirse en un CLAIM.

Ejemplo:

```text
CLAIM:
"El partido fue suspendido por lluvia."
```

El sistema almacena:

```text
claim
sources
source_type
source_timestamp
confidence
supporting_sources
contradicting_sources
status
```

Estados:

```text
CONFIRMED
SUPPORTED
UNCONFIRMED
CONTRADICTED
UNKNOWN
```

Si existen contradicciones:

```text
Fuente A → lluvia
Fuente B → falla eléctrica
Fuente C → iluminación

STATUS = CONTRADICTED
```

El BOT no debe presentar el motivo como hecho hasta resolver la contradicción.

---

# 20. DATO VS INTERPRETACIÓN VS PERSONALIDAD

Separar siempre:

## DATO

Lo que sabemos.

## INTERPRETACIÓN / CONTEXTO

Lo que las fuentes indican o lo que está siendo discutido.

## PERSONALIDAD

Lo que El Robot Futbolero agrega como personaje.

Ejemplo:

```text
DATO:
América recibió un penal al minuto 72.

CONTEXTO:
La decisión está generando discusión entre aficionados.

PERSONALIDAD:
"¿PENAL PARA EL AMÉRICA? Qué sorpresa… 🤖"
```

El LLM puede modificar la personalidad.

No puede modificar el dato confirmado.

# 28. REGLAS OBLIGATORIAS DEL FLASH

## GOAL

Debe incluir obligatoriamente:

* equipo que anotó;
* marcador actualizado;

> ⚽ GOOOOL DE QUERÉTARO.
>
> Querétaro 1-0 Guadalajara.


Regla:

```text

```

## RED CARD

Debe incluir:

* jugador;

* marcador actual si aplica.

## PENAL

Debe incluir:

* equipo beneficiado;

## MISSED PENALTY

Debe incluir:

## HALFTIME

Debe incluir marcador.

## FULL TIME

Debe incluir resultado final.

# 31. SUSPENSION CONTEXT

Si API-Football indica:

```text
SUSPENDED
```

El sistema puede saber que está suspendido sin necesariamente saber por qué.

Primer Flash:

> ⚠️ SE SUSPENDE EL PARTIDO.
>
> El partido no continuará en este momento. Estoy investigando qué pasó. 🤖

El Context Engine investiga el motivo.

Solo si existe confirmación suficiente:

> ⚠️ Partido suspendido por condiciones climáticas.

Si existen versiones contradictorias:

> ⚠️ Hay versiones distintas sobre por qué se suspendió el partido. Estoy revisando cuál es la correcta. 🤖

# 34. SUSPENDED MONITOR

Si un partido queda suspendido:

```text
LIVE
↓
SUSPENDED
↓
SUSPENSION MONITOR
```

No apagar el Worker.

Reducir frecuencia.

Ejemplo:

```text
LIVE
→ polling ~15s

SUSPENDED
→ polling ~60–120s
```

Si:

```text
SUSPENDED → LIVE
```

entonces:

```text
reactivar polling ~15s
↓
generar evento RESUMPTION
↓
evaluar publicación
```

Si:

```text
SUSPENDED → RESCHEDULED
```

guardar nueva fecha.

Si:

```text
SUSPENDED → FT
```

cerrar.

No existe un límite arbitrario de dos o tres horas.

---

# 35. STALE MATCH

Para evitar partidos zombis:

Si un partido permanece suspendido durante mucho tiempo sin cambios:

```text
SUSPENDED
↓
STALE
```

En STALE:

* detener polling intensivo;
* mantener monitorización de baja frecuencia;
* revisar nuevas actualizaciones;
* reactivar cuando exista una modificación relevante.

El Worker continúa vivo.

---

# 36. MATCH LOSS PROTECTION

Utilizar cuatro capas:

### 1. SYNC-MATCHES

Cada ~6 horas.

Consulta:

* ayer;
* hoy;
* próximos días.

### 2. FOOTBALL-ENGINE

Cada ~5 minutos.

Determina:

> ¿Qué debería estar pasando ahora?

### 3. LIVE WORKER

Monitorización persistente.

### 4. WATCHDOG

Cada ~10–15 minutos.

Busca:

* partidos estancados;
* Jobs fallidos;
* estados inconsistentes;
* eventos no procesados;
* Workers sin respuesta.

# STACK TÉCNICO OBLIGATORIO

El sistema debe utilizar **Next.js** como aplicación principal.

Next.js será responsable de:

* Dashboard / panel administrativo.
* API Routes / endpoints.
* Cron endpoints.
* Webhooks.
* Dashboard de partidos.
* Dashboard de Stories.
* Dashboard de eventos.
* Dashboard de Jobs.
* Monitoreo del sistema.
* Configuración editorial.
* Controles de pausa/emergencia.
* Integración con PostgreSQL.
* Orquestación de los servicios que no requieran un proceso persistente.

## IMPORTANTE

No utilizar Next.js/Vercel para polling persistente de partidos cada 15 segundos.

El polling LIVE debe ejecutarse en un:

**Render Background Worker**

El Worker será responsable de:

* consultar partidos activos;
* consultar API-Football;
* detectar eventos;
* actualizar PostgreSQL;
* crear Jobs;
* cambiar estados;
* manejar SUSPENDED → LIVE;
* ejecutar polling adaptativo.
